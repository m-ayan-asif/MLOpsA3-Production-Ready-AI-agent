## 2. System overview

My implementation has the following request and data flow:

1. A user sends a message to the FastAPI agent.
2. The orchestrator sends the conversation and the available tool schemas to Gemini. Automatic function execution is disabled; the application validates and executes selected tools.
3. Tool calls pass argument/schema validation, permission checks, confirmation gates for state changes, timeouts, and structured logging.
4. The tools query DVC/Git, MLflow, Airflow's REST API, or the Kubernetes API. A deterministic policy tool checks retraining evidence.
5. The agent returns an answer alongside a structured trace of the real tool calls and any failures.

The agent exposes **28 tools** across DVC, MLflow, Airflow, Kubernetes, and the retraining-evidence policy. The inference service runs in the `mlops-agent` namespace behind a ClusterIP Service. Docker Compose provides Airflow and MLflow; kind provides the local Kubernetes cluster.

The more detailed component diagram and permission matrix are in [architecture.md](../architecture.md).

## 7. Kubernetes deployment and diagnostics

I deployed `inference-api` in the `mlops-agent` namespace with:

- two replicas behind a ClusterIP Service;
- separate `/healthz` liveness and `/readyz` readiness probes;
- CPU/memory requests and limits;
- ConfigMap-based model/application version settings; and
- a namespace-scoped, least-privilege Role and RoleBinding for the agent.

During the live verification, the kind control-plane node was `Ready`, the inference Deployment was **2/2 ready**, and the Service had two ready endpoints. Requests through the Service returned HTTP 200 for `/healthz`, `/readyz`, and `/version`. A valid 30-feature prediction returned HTTP 200; a one-feature request was rejected with HTTP 422.

I kept liveness and readiness distinct: if model loading fails, the process can stay alive for diagnosis while readiness fails, removing the pod from Service endpoints. That avoids repeatedly restarting a diagnosable process and prevents traffic reaching a pod without a loaded model.

I designed the agent so the language model cannot authorize a state change. The API's `confirm` value is injected by the tool runtime and is not part of the LLM's tool schema. `airflow_trigger_dag`, `k8s_restart_deployment`, and `dvc_checkout_version` require explicit confirmation. Tools also validate arguments, enforce permissions and namespace restrictions, use timeouts, and produce structured traces/logs. Tool errors are surfaced to the model as unavailable evidence; the final response identifies failed calls, and an answer with no tool calls is flagged as unsupported.

All automated tests mock external systems, as the CI workflow specifies. The live checks above complement those tests; they do not mean the test suite itself ran against live Gemini/Airflow/MLflow/Kubernetes.
